All 4 phases — launch blockers, release automation, hardening, and go-live — were completed in a single intense push. The phased structure (blockers → automation → hardening → go-live) kept work focused and prevented scope creep between phases.

Issues #129–#143 were discovered during the RC4 staging test, filed, and resolved same-day. The tight find-file-fix loop from Sprint 001 continued to work well. Key fixes included reference bar visualization, marker matching improvements, affiliate referral links, and admin panel theme audit.

### 3. Release automation delivered real value immediately
Auto-deploy to staging (#122), snapshot checks in CI (#123), post-deploy smoke tests with version assertion (#124), and staging DB backup before migration (#127) all shipped. The post-deploy smoke test caught the version mismatch issue that led to discovering the compose file bug.

### 4. Rollback mechanism and error alerting shipped
deploy.sh rollback (#125) and Sentry integration (#126) were delivered as planned. These were identified in the Sprint 001 retro as must-haves before go-live, and both were completed.

### 5. Kundentyp persistence bug caught and fixed during RC4
The INSERT ON CONFLICT fix for the billing address save was discovered during live testing. The user_profile row didn't exist for some users, causing UPDATE to silently affect 0 rows. The fix was simple but would have been invisible without real-user testing.

v0.20.0 is live on app.sovereignhealth.io with all services healthy. The deploy pipeline (build → transfer → restart → verify) worked end-to-end once the compose file issue was resolved.

## What Could Be Better

### 1. Production compose file had wrong image names
The production `docker-compose.prod.yml` on the VPS referenced `registry.gitlab.com/sovereign-health/core-backend:latest` — a stale GitLab registry URL from the pre-GitHub migration era. The deploy script built and transferred `sovereign-health-backend:latest` correctly, but the compose file never used it. This meant the first production deploy silently ran the old image.

**Action:** Add a post-deploy verification step that checks `docker inspect` on the running container and compares its image ID to the just-transferred image. Also version-control the compose files in the repo so changes are tracked.

### 2. Docker build cache served stale binary despite source changes
Even with `--force-recreate`, the production backend container kept running the old image. Required `--no-cache` build + manual stop/rm/up to force the correct image. The root cause was the compose file issue above, but the symptom was confusing.

**Action:** The deploy script should verify the running container's image SHA matches the built image SHA after restart. Add this to the post-deploy smoke test (#124).

### 3. Version constant wasn't bumped with the RC tag
The VERSION constant in lib.rs stayed at `rc2` when deploy.sh was updated to `rc3`. Snapshot files also need updating. This was a manual coordination issue — 5 files need to change in sync.

**Action:** Create a `bump-version.sh` script that updates lib.rs, Cargo.toml, package.json (frontend + website), deploy.sh, and snapshot files in one command. This was identified in the Sprint 001 retro but not implemented.

### 4. No Cloudflare cache purge on production deploy
CF_ZONE_ID and CF_API_TOKEN weren't in the `.env` file at the path the deploy script checks. Cache purge had to be done manually via the Cloudflare dashboard.

**Action:** Ensure the `.env` file on the dev machine includes Cloudflare credentials, or add them to a separate `.env.deploy` that the script loads.

### 5. Sprint 002 scope expanded significantly from original plan
The original plan was 42 pts. RC4 testing added 15 new issues (~35 pts), plus admin audit log, info bar, and LOINC enrichment work. Total delivered was ~91+ pts. While velocity was high, this level of scope expansion makes planning less useful.

**Action:** Cap unplanned work at 20% of sprint capacity. File issues for next sprint instead of adding them mid-sprint. Exception: blockers found during RC testing.

## Incidents & Surprises

| Event | Impact | Resolution | Lesson |
|---|---|---|---|
| Prod compose had GitLab registry image names | All production deploys used stale rc2 image silently | Updated compose file on VPS to use local image names | Always verify container image ID post-deploy, not just HTTP status |
| Docker `--force-recreate` didn't pick up new image | Backend served old version despite successful deploy report | Stop + rm + up with corrected compose file | `--force-recreate` only recreates the container config, doesn't re-pull/re-resolve the image if the tag hasn't changed in the compose definition |
| Toast at 170px overlapped page content | Login welcome message covered health zone cards | Reduced offset to 16px (top of viewport) | Test toast positioning on all pages, not just the page where it was implemented |
| Kundentyp not persisting after save | Customer type reverted to "private" on tab switch | Added INSERT ON CONFLICT before UPDATE in settings handler | COALESCE-based updates silently do nothing if the row doesn't exist — always ensure the row exists first |

## Process & Workflow Changes

### Adopted This Sprint
- **Phased sprint structure** — Phases 1→2→3→4 with gates between them. Worked well for keeping focus.
- **Post-deploy version assertion** — deploy.sh now checks the API version matches the expected version after deploy. This is what caught the compose file issue.
- **Staging DB backup** — Automatic pg_dump before backend restarts. Already saved us from one schema migration issue.
- **Rollback support** — `deploy.sh rollback staging` works. Not yet tested in anger on production.

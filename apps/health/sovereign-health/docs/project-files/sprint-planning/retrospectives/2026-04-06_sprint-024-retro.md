# Sprint 024 Retrospective

**Sprint:** 024 - Pre-Launch Hardening
**Duration:** 2026-04-05 to 2026-04-06 (2 days)
**Points planned:** 33
**Points delivered:** 33
**Version:** v0.34.0 -> v0.35.0

## What Went Well

- **Demo data architecture** worked cleanly: 3 real accounts, API-imported CSV data (1,728 measurements), protected on production, free to reset on staging. The `DEPLOY_ENVIRONMENT` env var pattern is clean and reusable.
- **Security hardening** completed: ZAP findings fixed (CSP, HSTS, X-Frame-Options, X-Content-Type-Options), cargo audit documented, lucide-react 1.7 bumped without issues.
- **Learn page** on the website came together well after iteration - manually captured screenshots from the user were much higher quality than Playwright automation.
- **Parallel execution** of 3 morning tracks (audit, lucide-react, demo data) saved time on Day 1.
- **VPS maintenance** included: kernel updated (6.8.0-107), packages updated, full DB backups taken and downloaded locally.

## What Didn't Go Well

- **Screenshot automation** with Playwright was unreliable: basic auth on staging blocked access, rate limiting blocked DE login, locale cookie didn't switch button text. After 4 attempts, we used manually captured screenshots which were better quality anyway.
- **Learn page iterations** took 6 deploys to get right: wrong image order for DE, missing tooltips, video placeholder, section naming. Should have reviewed mockup before building.
- **Production deploy from wrong branch** happened again (3 failed attempts). The `run_in_background` tool starts a new shell that doesn't inherit the current git branch state. Must run deploy in foreground or verify branch inside the deploy script.
- **VPS compose files not auto-synced**: `DEPLOY_ENVIRONMENT` was in the local compose files but not on the VPS. Had to SSH and manually add it. The deploy script should sync compose files.

## Lessons Learned

1. **Manual screenshots beat automated ones** for marketing/learn pages. Playwright is for testing, not for content capture. User-taken screenshots show real data with proper context.
2. **DEPLOY_ENVIRONMENT pattern** for staging vs production guards is the right approach. Protected accounts only enforced in production, staging is fully testable.
3. **Demo data via API import** (not DB seeds) catches real pipeline bugs. The CSV import identified that the interactive confirm endpoint requires column mapping - batch import needed a direct SQL approach instead.
4. **Website and app are separate codebases** - learn page, marketing content, and public pages belong on the website (sovereignhealth.io), not the app (app.sovereignhealth.io).
5. **VPS compose files need syncing** - deploy.sh should copy updated compose files to the VPS, not just build/transfer images.

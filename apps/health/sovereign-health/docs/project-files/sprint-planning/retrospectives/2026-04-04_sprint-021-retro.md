## What Went Well

1. **Design-first + phased execution worked** — the 4-phase plan with parallel tracks (A/B in Phase 2, C/D in Phase 3) allowed maximum throughput without conflicts.

2. **Existing infrastructure saved time** — `lib/units.ts` already had `MARKER_UNIT_MAP` with 27 markers and bidirectional conversion factors. The `useUnitPreferences` hook just wired it up.

3. **DB audit triggers are the right abstraction** — captures every write with changed fields automatically, no per-handler instrumentation needed. 11 tables covered with one migration.

4. **Staging testing caught real bugs** — 7 issues found and fixed before production. The trigger PK bug and unit cache invalidation would have been production incidents.

5. **Auto-purge on startup** — simple, no external cron dependency. DSGVO retention enforced automatically.

---

## What Didn't Go Well

1. **Unit group design flaw** — insulin, HbA1c, vitamin_d share `glucose_unit` group but have incompatible unit values. The workaround (skip backend save for incompatible units) works but is a band-aid. Proper fix: give each marker its own unit preference field.

2. **Multiple staging deploys** — 5 deploy cycles to fix staging issues. Each deploy takes ~13 minutes. Total deploy time: ~65 minutes on fixes alone.

3. **Website data files kept getting modified** — staging/production deploys re-sync tier/content data, causing dirty working tree. Had to commit these repeatedly.

4. **Privacy/terms pages were placeholder stubs** — internal `/privacy` and `/terms` routes existed but showed "coming soon" text. Should have been external links from the start.

5. **Image size mismatch warnings** — every deploy shows FAIL for image size (local compressed vs remote uncompressed). Not a real failure but noisy.

---

## Key Lessons

1. **Unit preference groups must match 1:1 with backend fields** — sharing a group across markers with different unit sets causes save failures. Either add per-marker DB columns or validate on the frontend before saving.

2. **Module-level cache needs invalidation events** — any in-memory cache that persists across navigations must have an explicit invalidation mechanism. Custom events work well for cross-component communication.

3. **DB triggers need defensive PK handling** — not all tables have an `id` column. Use JSONB extraction (`(_new->>'id')::UUID`) instead of direct column access.

4. **Test unit toggles bidirectionally** — changing A→B may work while B→A fails due to caching. Always test both directions.

5. **Stash before promote** — the deploy script requires a clean working tree for production promote. Learned this again (feedback_stash_before_promote.md already existed).

## What Went Well

### 1. Parallel Dependabot resolution was highly efficient
All 6 Dependabot PRs (thiserror 2, rand 0.9, actix-governor 0.10, criterion 0.8, @base-ui/react 1.3, @types/node 25) were resolved in a single session by launching 5 parallel agents. The agents worked in isolated worktrees, and changes were merged back into develop cleanly. Total wall-clock time for all 6 dependency upgrades: ~5 minutes of agent work + ~15 minutes of manual integration and verification.

### 2. Three-layer protected users system prevents future data loss
After the demo user was accidentally deleted in the previous session, a comprehensive protection system was implemented: PostgreSQL BEFORE DELETE/UPDATE triggers, app-level 403 guard in the delete handler, and `is_protected` filter in the purge cron. Three independent layers mean a single bug can't cause data loss for critical accounts.

### 3. Release workflow overhaul — no more RC churn
The decision to drop RC tags in favor of full releases (minor for sprints, patch for fixes) simplifies the workflow significantly. The bump-version.sh script handles all 7 files + Cargo.lock in one command. The target of v0.21.21 by BTCPrague gives a clear patch version runway.

### 4. Five migrations shipped without issues
Migrations 098-102 (protected users, FK constraints, soft delete, indexes, retention policies) were designed to be idempotent (IF NOT EXISTS, ON CONFLICT DO NOTHING) and deployed successfully to staging on the first backend restart.

### 5. Release artifacts generated inline
The 4 required release artifacts (audit JSON, release notes, testing report, manual checklist) were generated as part of the commit flow, not as a separate task. This keeps documentation in sync with code.

## What Could Be Better

### 1. Frontend lockfile out of sync broke Docker build
After updating `@base-ui/react` and `@types/node` in `package.json`, the frontend's standalone `pnpm-lock.yaml` (used by Docker) wasn't regenerated. The first staging deploy failed with `ERR_PNPM_OUTDATED_LOCKFILE`. Required a second commit to fix.

**Action:** Add a lockfile sync check to the deploy script pre-flight: compare `package.json` specifiers against `pnpm-lock.yaml` specifiers before building. Or better: add a pre-commit hook that runs `pnpm install --frozen-lockfile` in the frontend dir and fails if it errors.

### 2. Worktree agents applied incomplete changes
The rand and actix-governor agents worked in isolated worktrees but their code changes didn't automatically flow back to the main branch. Manual cherry-picking of each change was needed. The rand agent's `affiliate.rs` change was initially missed, causing a compilation failure.

**Action:** When using worktree agents for dependency upgrades, always run a full `cargo check` on the main branch after applying all changes — not just trust the individual agent results.

### 3. Demo user decision changed mid-session
The sprint plan called for removing the demo user from production (P4-1). Mid-session, the decision changed to keep the demo user on production (it's the public preview model) and protect it instead. This is fine — priorities shift — but the sprint plan wasn't updated in real time, creating a gap between the plan and reality.

**Action:** When a sprint task changes scope or direction, update the sprint doc immediately, even if informally. A quick `P4-1: CHANGED — keep demo user, add protection` note prevents confusion.

### 4. Phase 3 not started — sprint scope was realistic but time-limited
Phase 3 (Analysis tab, Playwright E2E, release notes) was 19 pts of the 46 planned. None was started because Phases 1, 1b, 2, and 4 filled the day. This was correctly predicted as a risk in the sprint plan ("E2E tests are a stretch goal"), but it still means ~40% of planned work carries over.

**Action:** For single-day sprints, plan 25 pts max. Reserve Phase 3-level feature work for multi-day sprints.

### 5. cargo fmt auto-reformatted files we didn't touch
Running `cargo fmt` as part of the lint check reformatted several handler files (affiliate.rs, billing.rs, etc.) that had pre-existing formatting issues. These changes got mixed into the release commit, making the diff noisier than necessary.

**Action:** Run `cargo fmt` as a separate commit before starting sprint work, so formatting changes don't pollute feature/fix commits.

## Process & Workflow Changes

### Adopted This Sprint
- **Full releases, no RCs** — Every version is a complete release (0.21.0, not 0.21.0-rc1). Deploy to staging first, verify, promote to production.
- **Patch version strategy** — Minor bumps for sprint releases, patch bumps for quick fixes. Target: v0.21.21 by BTCPrague.
- **bump-version.sh** — Single command updates all 7 version files + Cargo.lock. Eliminates version drift.
- **Parallel worktree agents** — Dependabot PRs resolved by launching multiple agents in isolated git worktrees. Fast but requires manual integration.
- **Release artifacts inline** — 4 artifacts (audit JSON, release notes, testing report, manual checklist) generated as part of the commit flow.
- **Weekly reports on Fridays only** — No mid-week summary reports.

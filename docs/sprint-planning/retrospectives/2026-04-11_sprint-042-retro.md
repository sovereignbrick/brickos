## What Went Well

### 1. The "fix the issue, ship the fix in the same session" pattern was fast

Every Sprint 042 phase was: identify the file:line → write the fix → test locally → commit → deploy to staging → verify with API smoke. 5 issues closed end-to-end in one session, including 6 deploys. The user feedback loop was tight: when they reported a tab order regression after Phase D, the fix was committed and deployed within ~5 minutes.

The pattern only works because (a) the fixes were small and well-understood by the time we got to them, and (b) the deploy.sh script + the Sprint 042 #538 SW cache fix make redeploys cheap. **Action:** keep doing this for the smaller bug-fix sprints. Architecture sprints need a different cadence.

### 2. Phase D had to ship three times -- and that was fine

Phase D #528 settings restructure went through three commits before landing in the right shape:

- Iteration 1: brickos-master-first order, Notifications + Billing as standalone tabs
- Iteration 2: production-order corrected (SHI tabs first, brickos master after)
- Iteration 3: per the user's correction, Notifications + Billing folded back into Account as inline sections

Each iteration was 5-15 minutes from "user feedback" to "deployed and verified". The third iteration was the first one that matched the production layout the user was actually showing me. **The lesson:** when the user references "production version", get a screenshot of the production version BEFORE proposing the new layout. I should have asked for the production screenshot when I proposed the brickos-master-first split in the first place.

### 3. Phase A's revised plan caught a real bug before it shipped

Original Phase A plan: "drop the new `brickos.tier_features` (slug-based) as dead code". Revised plan when I actually read the code: **the new shape is queried by `brickos-licensing::EmbeddedProvider::tier_features()` -- it's NOT dead code at the crate level**, only at the SHI handler level. Dropping it would have broken the brickos-licensing crate.

This is exactly what `feedback_never_ship_half_schema_migration.md` warns about, applied to the inverse case: don't drop a table because one set of consumers isn't using it; check ALL consumers. **Action:** the same grep-before-drop pattern works for tables AND functions. Add to the memory rule.

### 4. Phase F had a pre-flight + post-flight design that caught both classes of bug

`#531` glucose unit confusion is fixed at TWO layers:

- **Frontend pre-flight** (`plausibilityHint()`): catches the most common case BEFORE submit. The user gets a confirm() dialog with the hint and a "Save anyway?" button. No round-trip needed.
- **Backend post-flight** (`unit_confusion_hint()`): catches anything the frontend missed. Same hint, same numbers, in the user's input units. The error message references the user's actual numbers.

Both layers use the same hint logic (separately implemented). The frontend layer is the UX optimization; the backend layer is the truth. This is the right defense-in-depth pattern for any input that has multiple valid units.

### 5. The brickos master template default decision came from one user message

The user's clarification "the setting where here before the brickos elevation. the idea is that each app has its own app settings, and brickos provides the template for generic setting information" -- one paragraph -- gave me everything I needed to understand the architectural intent. I listed all the settings, proposed a categorization, asked for input, and the user confirmed in one round. Then a single follow-up screenshot ("billing and notifications should be embedded under Account") corrected my assumption. **Three messages from the user, one fully-shipped restructure.**

## What Could Be Better

### 1. I shipped the wrong tab order TWICE before getting it right

Phase D landed three times. The first two iterations were wasted work because I was guessing at "the right" tab order instead of looking at production. The fix was a screenshot of the actual production page, which the user provided after iteration 2.

**Action:** when the user references "the current production version" of anything (UI, behavior, layout), the FIRST step should be "show me a screenshot of production" or "give me the URL of production". Don't guess.

### 2. The display_value / value split was a second iteration

Phase F first landed with `value: canonical, unit: displayUnit`. The validator read "0.277 mg/dL" which was technically correct but completely useless to the user. The user found the bug, I added `display_value` as a separate field, and shipped iteration 2.

The mistake was thinking "the validator just needs the unit" without checking that the value field was already canonical. The fix was tiny -- one field on the model, one branch in the handler -- but it should have been right the first time.

**Action:** when extending a validator, trace the data flow end-to-end before writing the code. Frontend → request body → handler → validator. If any step does a transformation, the validator's input may not be what you think.

### 3. Phase A's "remaining work" was unclear at the time

After committing the codified migration (`308c80c`), I marked Phase A as "partially done" because the bootstrap migration could still be tidied to do `SET SCHEMA public` directly instead of rename-aside-then-fix-up. But the "tidy" was never actually a blocker -- it was cosmetic, and trying to land it would have triggered another `_sqlx_migrations` checksum dance.

This sprint Phase A is **functionally complete**. The cosmetic tidy is opportunistic cleanup, not Sprint 042 scope. I should have closed #527 immediately after `308c80c` instead of leaving it in "partially done" purgatory for the rest of the sprint.

**Action:** when a fix is functionally complete, close the issue. "Partially done because there's a nicer way to write it" is not a reason to leave an issue open.

### 4. The brickos.io URL namespace consolidation (#526) is starting to be a recurring blocker

Sprint 041 hit it (newsletter export CORS preflight). Sprint 042 hit it again (SW cache and per-app PWA install both have "post #526 this auto-DTRT" comments in the code). Sprint 043 has it as Phase C. **Three sprints in a row with #526 as a deferred item.**

**Action:** Sprint 043 must actually ship #526. The design 015 can't be "drafted later" -- it's the gating doc. Action item: write the design doc as the FIRST thing in Sprint 043, before any code.

### 5. Sprint 042 had no bake monitor run

Sprint 041 ran the bake monitor for 1h45m and caught the #527 product_features errors in the actual window the user was reporting them. Sprint 042 didn't run the monitor at all -- I made 6 deploys without ever turning it on. The deploys went fine, but the absence of the monitor means I have no proof that the in-sprint changes didn't introduce a slow-burn issue.

**Action:** every sprint that ships to staging must run the bake monitor for at least 30 min after the last deploy. Add to the deploy.sh as a post-step (this is a Sprint 043 cleanup).

## What Went Well

### 1. Design-first approach made execution almost mechanical

Design 022 was finalized before any code was touched, and the 30 issues were written out in full (scope + verification + acceptance) before Phase A started. Once execution began, every issue had a clear contract and almost zero scope debate. This is the third sprint in a row where design-first produced zero rework — the pattern is proving itself. Memory `feedback_design_first_sprints.md` already captures this; no update needed.

### 2. Additive schema migration strategy de-risked the critical path

Migration 009 (#460) only created NEW tables in the brickos schema alongside the legacy SHI `public.tier_features` / `product_features`. The alternative — dropping and replacing — would have been a hard break. The additive approach kept SHI fully working throughout Phase B while the new path was stood up, with shadow-mode validation (#467 part 2) catching any divergence before the canonical flip in part 3. Zero regressions, zero downtime pressure, clean deprecation path via the deferred #490 cleanup.

### 3. 3-state safety net paid off during the tier.rs facade refactor

`LICENSING_USE_NEW_PATH` + `LICENSING_SHADOW_MODE` env vars meant the canonical flip in `check_feature` was a two-line change that could be rolled back via env var, not code. The matrix test (#470) ran against both paths simultaneously and would have caught any divergence immediately. This is the pattern to use for any future `rewrite this big thing` refactor — a shadow mode + an env flag is cheaper than a branch.

### 4. EmbeddedProvider avoided N+1 queries by default

When building the #478 org detail handler, extending the single query with FILTER aggregates for owners/practitioners/members + DISTINCT ON for the active license turned what would have been 4-5 follow-up API calls into one. Same pattern in #477 for the list view. The admin GUI is fast because the queries are thick, not because the frontend is optimized.

### 5. Cron-driven tracker sync stayed out of the way

The auto-sync.sh hardening (from cron fire #1) meant that for the rest of the sprint, hourly cron fires just drained the issue backlog in the background without blocking work. Each fire created ~20 issues and gave a short 1-3 line report. The per-run cap + skip flag + self-heal on 422 turned "sync all or nothing" into "steady drain over hours". Pattern is now captured in memory `feedback_bash_sync_script_hardening.md` and is reusable for any future bulk sync script.

### 6. Backend + frontend in lockstep avoided mid-sprint rework

Every Phase D commit landed backend + api helper + frontend + i18n in one commit. No "frontend expects a field the backend doesn't return yet" gaps. The pattern was: write the SQL query first, then extend the api.ts type, then build the UI, then add i18n, then run the full check cycle (clippy + fmt + tsc + tests + build). Slow per commit but fast across the whole phase.

### 7. Shipped the whole phase in one day

Phases A through E in a single day is compressed even by this repo's standards. The design-first + additive migrations + 3-state safety net + EmbeddedProvider patterns combined made it possible. The alternative (multi-week rollout with production deploys gating each phase) would have been safer in theory but would have lost the momentum that made the refactor feel ergonomic.

## What Could Be Better

### 1. #471 Playwright suite skeleton is skeleton-only

The suite was delivered but Journeys 3 and 4 are gated on `E2E_TWO_POOL_READY=1` because they require the brickos schema to exist in a separate DB. In the single-DB local dev environment there is no such DB, and the brickos-db migrations 004/005 have pre-existing bugs that block a single-DB workaround. This means the E2E coverage for the admin override + org member seat enforcement journeys is zero until #491 ships.

**Action:** #491 is the first issue of Sprint 041. Option A (true two-DB E2E setup) is the recommendation.

### 2. Single-day execution traded safety for speed

No tests ran against a real brickos schema in the SHI CI pipeline during this sprint. The EmbeddedProvider code paths touching `brickos.org_licenses` / `brickos.feature_registry` are only exercised by the crate's own `embedded_runtime` test (which spins up its own postgres). The admin GUI backend endpoints will discover any brickos schema mismatches the first time they're hit against staging. The dead-code cleanup #490 deliberately gates on "shadow mode clean on staging for 2-4 hours" — that check cannot happen until someone deploys.

**Action:** Before closing #491, add a CI job that applies brickos-db migrations + runs `cargo test --test tier_feature_matrix_test` with `TEST_DATABASE_URL` pointing at the two-pool fixture. That's the first line of defense for the platform admin endpoints.

### 3. Website i18n for customer-facing licensing page is EN-only

The `/licensing` page on sovereignhealth.io is EN-only, same as the rest of the website. DE translation is a follow-up. The SHI app itself is fully bilingual, and the admin GUI has EN+DE, but the marketing/legal pages are still catching up. This isn't a regression introduced by Sprint 040; it's a visible gap.

**Action:** When the website gets its route-level i18n pass (separate Phase), translate `/licensing` + `/terms` + `/privacy` together. Low priority until we have a DE-speaking customer.

### 4. Branding column live in two places (SHI vs brickos schema)

The `organizations.branding` JSONB column was added to both the SHI public.organizations table (migration `20260410000030`) AND brickos.organizations (migration `007_org_branding.sql`). Same for `domain_mappings`. This works in both single-DB and two-pool deploys but is exactly the kind of parallel-schema situation that `#490` dead code cleanup is supposed to eliminate. A SHI app running against the two-pool production DB will be reading branding from SHI.public.organizations, not brickos.organizations, unless the query is qualified. The #478 `list_organizations` query is unqualified, so it follows search_path.

**Action:** Add to #490 cleanup: verify that every query on `organizations` either (a) uses an explicit schema or (b) has a deterministic search_path set. The local dev migration is a stopgap and should be removed once #491 two-pool is the only supported local setup.

### 5. No manual smoke of Phase D admin screens

Every commit passed clippy + fmt + tsc + tests + pnpm build, but no browser smoke test was performed against a running dev stack. The admin Orgs list view, org detail tabs, license generation form, branding tab, invoices tab, and dormant user review all compile and typecheck — but none of them have been clicked through. First real click-through will happen the first time someone runs the dev stack.

**Action:** Sprint 041 Day 1 should include a "drive-through" smoke session: spin up a dev stack, walk every admin screen, fix anything broken. Document the "happy path" script so it can be re-run for every future admin GUI change.

### 6. Retrospective format doesn't map to single-day sprints

This template is designed for multi-day sprints with daily stand-ups, staging deploys, and velocity trends. Forcing a single-day sprint into it creates sections that are either empty (Mood Check across zero days) or trivially full (every metric is "this sprint"). The retrospective still has value — the lessons captured above are real — but the format friction suggests a second template for compressed sprints.

**Action:** After a few more single-day sprints, decide whether to fork the template or just accept that some sections go empty. For now, leaving it as-is.

## Process & Workflow Changes

### Adopted This Sprint

- **Design-first sprint kickoff** — design 022 v2 was signed off before any code; issues were fully written (scope + verification) before Phase A started. Third sprint using this; promoting from "new thing" to "default".
- **3-state shadow mode for the big refactor** — `LICENSING_USE_NEW_PATH` + `LICENSING_SHADOW_MODE` env flags let #467 be a zero-risk flip. Pattern is reusable for any future `rewrite this thing` refactor.
- **Additive migrations with deferred cleanup** — migration 009 added NEW tables in brickos schema alongside legacy SHI tables; the drop happens in #490 only after shadow mode validates parity. Pattern: never drop and replace in the same sprint.
- **Per-issue lockstep commits** — backend + api.ts + frontend + i18n all land in one commit per issue. Slower per commit, faster per phase.
- **Phase C email templates are bilingual by construction** — every template has an EN + DE variant and a sweep test asserting every lifecycle template contains BrickOS branding and never "Sovereign Health". Pattern prevents monolingual regressions.

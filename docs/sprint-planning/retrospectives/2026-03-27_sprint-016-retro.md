## What Went Well

1. **Production bug hunt was effective** -- found 5 real bugs by actually using the app in production. Manual testing beats automated tests for UX issues (duplicate markers, missing year, unnecessary fields).

2. **Critical migration issue caught and fixed quickly** -- Dr. Alex was blocked for paying Clarity user because migrations didn't apply on production (demo seed migration tried to cast encrypted values to float). Diagnosed in 10 min, fixed by manually marking migration as applied, backend restarted, all 9 pending migrations ran.

3. **Backfill endpoint is powerful** -- computed 2,166 historical calculated marker values in one API call. User now has complete Dr. Boz, GKI, BMI, WHtR, HOMA-IR, HCT/HB trend data for their entire measurement history.

4. **Log analysis clean** -- zero production errors, pgAudit working correctly, Gatus healthy. Good signal that v0.29.1 is stable.

---

## What Didn't Go Well

1. **Migration that reads user data failed on production** -- `20260326000001` (demo seed) used `value_canonical::float8` which works on staging (plaintext demo data) but fails on production (encrypted values). **Critical lesson: migrations must NEVER assume plaintext values.** This blocked ALL subsequent migrations including `ai_credit_usage`, causing Dr. Alex to fail for all users.

2. **Backfill created phantom calculated markers** -- first version iterated ALL measurement timestamps, and enrichment pulled glucose/ketones from other dates, creating Dr. Boz entries at timestamps where glucose/ketones were never measured. Required 3 iterations to fix:
   - v1: iterate all timestamps (wrong)
   - v2: iterate only calc-input timestamps (better but still wrong)
   - v3: filter by direct-input requirement per marker (correct)

3. **OpenVAS SCAP database corruption** -- the first-run SCAP import failed silently, leaving a corrupt state that caused restart loops. Required full data wipe and fresh start. The immauss/openvas container doesn't handle interrupted SCAP imports gracefully.

4. **Deploy branch check race condition** -- twice the deploy.sh failed because I switched from main to develop while deploy was still running. deploy.sh checks the current branch during verification, not just at start.

---

## Key Lessons

1. **Migrations that read measurements MUST handle encryption.** Either:
   - Guard with `WHERE is_demo = true` (demo data is plaintext)
   - Use application-layer Encryptor (not raw SQL casts)
   - Or skip entirely on production (demo seeds aren't needed there)

2. **Calculated marker backfill needs per-marker input validation.** Each formula has specific required inputs -- enrichment should fill gaps within the same logical session, not create new data points at unrelated timestamps.

3. **Don't switch git branches during deploy.** Wait for deploy.sh to complete fully before changing branches.

4. **OpenVAS needs a stable network for first-run feed sync.** Budget 30-45 min for initial setup. If interrupted, wipe and start fresh rather than debugging corrupt state.

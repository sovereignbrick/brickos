## What Went Well

### 1. Planning session produced three major deliverables before any code
The conversation covered issue tracker design, PWA audit, URL shortener architecture, Start9 product vision, and shared design system — all before writing a single line of implementation code. This meant zero rework during coding. Every design question was resolved upfront.

### 2. First cross-app crate architecture worked cleanly
Sovereign Link as a library crate imported by the health API is the right pattern. `configure_routes()` mounts cleanly, `LinkStore` trait allows future backend swaps, and the crate compiles independently. The workspace dependency wiring (`sovereign-link = { path = "..." }`) was straightforward.

### 3. 2-char app prefix system is elegant
Auto-codes (`sha3f2c1b9`) route without any DB lookup — the handler reads the prefix, looks up `app_prefixes` (cached), and builds the redirect URL. Vanity codes (`drclinic`) are globally unique and use DB lookup. This gives us both speed and clean promotional URLs.

### 4. Local issue tracker fills a real gap
With GitHub API rate-limited, the `docs/tracker/` system with `git mv` to close issues and `sync.sh` for future restore gives us sovereign project management. 98 issues catalogued from sprint docs in one session.

### 5. Product thinking expanded scope constructively
The shortener evolved from "affiliate links" to a dual-mode product (BrickOS platform + Sovereign Link for Start9) through conversation. The 2-char prefix, reverse proxy vision, and BrickOS Relay concept all emerged naturally. Planning and implementation stayed on the same day.

## What Could Be Better

### 1. Dockerfile not updated for new workspace crate
The Docker build context only copied `crates/`, `platform/`, and `apps/health/`. Adding `sovereign-link` under `apps/technology/` required adding two COPY lines to the Dockerfile (planner + builder stages). Failed on first deploy attempt.

**Action:** Checklist item for any new workspace crate: "Update Dockerfile COPY statements for all apps that depend on the new crate."

### 2. VERSION constant left at -b1 from previous deploy
The deploy script bumps `lib.rs` VERSION to `-b1` for staging, but the pre-flight check then fails on the next deploy because it expects the base version. Had to manually reset VERSION before each deploy attempt. Three failed deploy attempts before success.

**Action:** The deploy script should reset VERSION to base before the pre-flight check, or the check should strip the `-bN` suffix for comparison. Fix in deploy.sh.

### 3. Subagent Write permissions blocked file creation
Three background agents were launched to create tracker files (milestones, open issues, closed issues). Two had Write permission denied and wasted ~2 minutes. The open issues agent succeeded because it used Bash fallback. Had to create milestones and closed issues manually with Bash.

**Action:** For bulk file creation, use Bash with heredocs directly instead of delegating to subagents with Write tool.

### 4. No tests for sovereign-link handlers
The crate compiles and passes clippy, but there are zero unit or integration tests. The redirect handler, vanity validation, and click recording logic are all untested. Relying entirely on staging verification.

**Action:** Sprint 011 or 012 should add at minimum: redirect handler test (fast path + slow path), vanity code validation test, and click recording test.

## What Went Well

### 1. Manual session + bake monitor caught everything

The combination of (1) the user manually clicking through the platform admin GUI in real-time and (2) the background bake monitor scraping logs every 15 minutes turned out to be the most efficient bug-discovery loop of the sprint. The bake monitor's window 6 entry (3 errors) appeared **at exactly the moment** the user reported "Smart Import not working" -- automatic correlation with no extra effort. This cost almost nothing to set up (one bash script + nohup) and surfaced the P0 #527 bug within minutes of it being triggered.

**Action:** Make this the standard pattern for every staging deploy from now on. Memory entry already exists; promote to a deploy.sh hook in Sprint 042.

### 2. Tier 1 + Tier 2 fix batch shipped 6 issues in one commit

When the user said "fix the identified issues", the most efficient response was to batch the small fixes by impact and ship them as one PR-equivalent commit, then verify them all post-deploy in one round. Tier 1 (5 one-line frontend fixes) + Tier 2 (one backend filter fix touching 2 handlers) closed 6 issues in commit `2172ccb` and a single redeploy. The alternative -- one issue, one commit, one redeploy -- would have meant 4-5 redeploys, each ~7 minutes.

**Action:** Keep doing this. The pattern is "stage all small fixes locally first, build/test, then deploy once".

### 3. The conditional dual-write pattern (`to_regclass`) finally clicked

Sprint 041 had to deal with three different schema realities:
- Dev: dual schema (legacy `public.*` + `brickos.*` mirrors)
- Staging: single schema (`brickos.*` only, post `SET SCHEMA`)
- Production: would be the same as staging once Sprint 042 lands

The `SELECT to_regclass('public.foo') IS NOT NULL` runtime check made the same Rust code work in all three. After the third or fourth handler that needed it, the pattern became muscle memory. **By Sprint 042 this should be a `pub fn detect_dual_schema(pool) -> bool` helper called once per handler chain instead of repeated inline.**

**Action:** Extract the helper. Memory entry `feedback_dual_schema_fk_cleanup.md` already documents the lesson.

### 4. The local issue tracker scaled to 13 sprint-discovered bugs

Every bug got a numbered file, frontmatter, full repro steps, root cause analysis, fix paths with trade-offs, and acceptance criteria. The user could click a screenshot, I could file a bug with a 30-second turnaround, and the file became the durable carry-over artefact. This is much better than slack messages or in-conversation TODOs because future-Claude (Sprint 042) reads the file directly and has full context.

### 5. The sprint scope discipline held (mostly)

Bucket-3 issues (operational gaps) like #538 (service worker cache) were filed and immediately deferred instead of being worked in-sprint. Same for the architecture issues (#526, #528, #529). This prevented Sprint 041 from stretching into a 5-day sprint when its scope was 2 days. The lesson from `feedback_sprint_scope.md` ("Max 25 pts for single-day sprints") was honored.

### 6. The PR-based flow ran cleanly for the close-out

Sprint 040's close-out used the new ADR-048 PR-based flow for the first time. Sprint 041 dogfooded it again and it worked. No surprises, no merge conflicts, no broken hooks. The close-out runbook at `docs/runbooks/sprint-close-out.md` was followed step-by-step and produced this retro/review/milestone trio.

## What Could Be Better

### 1. Three different "feature catalog" schemas existed at once and nobody knew

`brickos.product_features` (legacy SHI), `brickos.tier_features` (legacy with `tier_key, feature_id` UUID), `brickos.tier_features` (new with `tier_slug, feature_slug` -- only created on staging by the bootstrap migration) all coexisted. The Rust handlers query the legacy. Sprint 040 #467 created the new shape and seeded 156 rows but never wired it to anything. Sprint 041's bootstrap migration assumed the new shape would be canonical, renamed the legacy aside, and broke everything on staging.

**Why it happened:** Sprint 040 #467 was a "shadow refactor" that landed the new schema but left the handler-side flip for "later". "Later" turned out to be "never", and Sprint 041's bootstrap migration was written by someone (me) who believed the flip had happened.

**Action:** Memory entry `feedback_grep_schema_before_migration.md` already exists. Promote it to a stronger rule: **before writing any migration that renames a table, grep the entire workspace for queries against that table** -- not just the SQL files, also `.rs` and `.ts`. If the grep finds queries, the migration is wrong.

### 2. The new `brickos.tier_features` was never queried -- it was dead code from day 1

Sprint 040 #467 created `brickos.tier_features (tier_slug, feature_slug)` and seeded 156 rows. **Zero handlers query it.** It's a tier-feature *mapping* table without the feature *catalog* it would join against. Sprint 041 only discovered this when revising #527's fix plan.

**Why it happened:** The slug-based redesign needs **both** tables migrated together: `tier_features` AND `product_features` (catalog). #467 migrated half the data model and shipped. The other half was never scoped.

**Action:** Sprint 042 #527 explicitly chooses option C (delete the dead new shape, keep legacy as canonical) and defers the slug-based redesign as a coordinated future-Sprint refactor. Document the rule: **never ship half a schema migration.** Either ship the new schema *and* its handler users in the same PR, or don't ship the new schema at all.

### 3. The bake monitor was set up but no error rate threshold tuning happened

The monitor's abort threshold was `>150 errors per 15min window`. The actual session saw windows of 3 and 5 errors. The threshold was so loose it might as well not exist. A 10/min sustained rate (the per-issue requirement) translates to 150/15min, which was the threshold. So the math is right, but the practical signal was useless until the user manually noticed.

**Action:** Tune the threshold to detect the *first* anomaly above baseline rather than the catastrophic fire. Specifically: alert when window N has more errors than the trailing 5-window average + a small margin. This catches the 3-errors window 6 because the trailing average is 0.

### 4. Service worker cache silently broke the deploy verification

The user clicked "Export CSV" after the #534 fix landed and still hit `NetworkError`. I had to dig into the chunk JS, confirm the fix shipped, then realize the service worker was serving the old code from cache. **The deploy verification step said the fix worked when, for any returning user with a cached SW, it didn't.**

**Why it happened:** The deploy.sh smoke checks hit the API directly, not via a browser. The actual user experience requires browser cache invalidation, which the smoke test never exercises.

**Action:** #538 captures the proper fix (nginx no-cache + serwist skipWaiting). Plus a deploy.sh verification step that asserts `Cache-Control: no-cache` on `/sw.js` after every redeploy.

### 5. The "Individual User" pseudo-org was a real DB row but used as a virtual category in the UI

The dropdown showed "Individual User" as if it were a real org you could navigate to, but the backend handlers expected `WHERE owner_org_id IS NULL` semantics for that label. The two interpretations disagreed silently and the filter returned 0 results. This same root cause hit 2 different pages (#536, #537) before I noticed they shared a layout component.

**Why it happened:** When the seed migration created the `Individual User` row in `brickos.organizations`, no handler was updated to special-case it. The seed and the consumers shipped in different sprints by different agents.

**Action:** The hotfix special-cases the UUID at the handler level. The proper fix (drop the seed row, build the UI category from `IS NULL` only) is captured in #536/#537 for Sprint 042. Plus a memory rule: **synthetic UI categories that look like real DB rows must be wired up at every consumer or they're a trap.**

### 6. The Dr. Alex AI provider config and the `/platform/ai/config` page were both stub implementations

`/platform/ai/config` had no `onClick`, no `onChange`, no save button. Dr. Alex was hardcoded to a single provider/model. Both shipped in Sprint 040 as "placeholder for future". Sprint 041 found them when the user clicked Test Connection and got no feedback.

**Why it happened:** Sprint 040 was a 1-day compressed push. "Build the page later" was the explicit trade-off and it was the right call at the time. But there was no follow-up issue filed for "go back and finish the AI config page".

**Action:** Whenever Sprint NNN ships a stub for "later", file the follow-up issue **in the same PR** that ships the stub, with a `stub-page` label. Sprint NNN+1's audit (#525-style) catches them.

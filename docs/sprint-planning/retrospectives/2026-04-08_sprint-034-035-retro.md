## What Went Well

1. **Design-first approach** -- writing specs 016/017/018 before coding meant zero rework. The ADRs captured decisions cleanly.

2. **Parallel agent execution** -- up to 4 agents working simultaneously on independent files. No merge conflicts. Massive throughput.

3. **Incremental deployment** -- staging first, verify, then production. Dual-routing (SLI alongside SHI) eliminated downtime risk.

4. **Backward compatibility** -- PlatformPool falls back to single DB. SHI works with or without SHI_PLATFORM_DATABASE_URL. Zero-downtime upgrade path.

5. **Layer-by-layer handler migration** -- auth first (highest impact), then billing (most complex), then remaining. Each group verified independently.

---

## What Could Be Better

1. **Worktree branch confusion** -- agents branched from `main` not `develop`, causing sovereign-link references to reappear. Required manual fixes after merge. Solution: always specify base branch for worktree agents.

2. **GLIBC mismatch** -- locally built binary didn't run on debian:bookworm-slim. Had to use deploy.sh Docker build. Solution: always use Docker builds for deployment, never transfer raw binaries.

3. **Config.rs overwrites** -- agent O's config.rs overwrote agent #393's platform fields. Multiple agents modifying the same file creates merge risk. Solution: serialize changes to shared files, don't parallelize.

4. **Port collision** -- SLI was planned for 8082 but Gatus already uses it. Had to use 8084 in production. Solution: maintain a port allocation registry in the design doc.

5. **Deploy.sh background output** -- background command output was empty. Deploy.sh uses interactive features that don't work well in background mode. Solution: use foreground for deploys.

## Decisions Made

| Decision | Rationale |
|----------|-----------|
| Separate DB per app | Multi-VPS scaling, EU/US data residency, independent backup |
| 3-char prefix (shi, sli, svo, scr) | Consistent naming across Docker, env vars, containers, DBs |
| PlatformPool newtype pattern | Distinguish two pools at compile time via Actix extractors |
| Service account API for inter-app calls | Clean separation, audit trail, encrypted communication |
| Content strings per app DB | No platform mixture, each app owns its translations |
| brickos-platform-api NOW (not deferred) | Platform admin routes must not live inside app code |
